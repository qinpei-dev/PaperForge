# PaperForge 知识库使用规范（docs/knowledge/README.md）

> 本目录是 PaperForge 对外表达的唯一事实来源。以后做小红书、抖音、项目介绍、简历、复盘时，**禁止依赖聊天记忆**，必须优先读取本目录事实库。

## 目录文件

| 文件 | 用途 |
|---|---|
| `PROJECT_FACTS.md` | 长期稳定、已确认的项目事实（身份/定位/功能/技术栈/地址/能力/边界/不能夸大的红线） |
| `PROJECT_HISTORY.md` | 按时间顺序的真实历史事件（日期/事件/证据/状态/是否适合对外宣传） |
| `CONTENT_EVIDENCE.md` | 宣传内容真实性控制（每条内容的已确认事实/可公开表述/禁止表述/尚未确认） |

## 强制流程（AI 工作流）

**凡涉及 PaperForge 的以下主题，动手前必须先读取上述三个事实库文件：**

- 项目经历 / 开发过程
- Bug / 验收 / 测试
- 版本 / 发布 / 上线
- 产品能力 / 技术栈 / 定位
- 对外宣传（小红书、抖音、简历、作品集、复盘、采访口径）

**顺序：**
1. 读取 `docs/knowledge/` 三个文件；
2. 关键事实与当前 Git/代码交叉核验（`git log`、当前代码、PROJECT_STATUS.md 等）；
3. 引用时在产物中标注证据来源（文件路径 / commit / tag / "来源：用户一手确认"）。

## 冲突与缺失处理

1. **事实库与当前 Git/代码冲突**：以当前代码和 Git 为准，**并立即更新事实库**（改后更新"最后核验日期"）。
2. **事实库中没有**：不得自动补全为"用户真实经历"；一律标记为"未确认"，需要时向用户本人确认并标注"来源：用户一手确认"。
3. **聊天记录 ≠ 证据**：聊天中出现的说法，只有用户本人确认后才可标为"用户一手确认"；不能伪装成 Git/代码/文档证据。
4. **先核实再写**：拿不准的表述对照 `CONTENT_EVIDENCE.md` 的"禁止表述"列；宁可少写，不写猜测。

## 事实来源优先级

1. **第一优先级**：Git log / Git diff / commit / 当前代码 / PROJECT_STATUS.md / AI_CONTEXT.md / 测试结果 / 生产部署记录
2. **第二优先级**：仓库已有 Markdown 文档、截图、release/tag、changelog
3. **第三优先级**：当前宣传项目中已经确认过的事实（如 D:\豆包宣传 的内容选题库/发布记录）

## 严禁事项

- 根据常识补剧情
- 根据代码推断"用户当时一定经历过什么"
- 编造时间、耗时、修复过程
- 把"可能"写成"已发生"
- 把不存在的自动化测试写成已运行
- 把"来源：用户一手确认"伪装成 Git 或代码证据

## 更新纪律

- 任何涉及 PaperForge 的任务结束后，若产生了新的已确认事实（新发布、新 Bug、新验收、新边界），**必须同步更新对应事实库文件**；
- 事实库只收已确认事实，不收短期任务、猜测、进行中状态；
- 每次更新后刷新文件头部的"最后核验日期"。

## 与营销项目的关系

- 营销项目（D:\豆包宣传：内容选题库.md / CURRENT_STATE.md / 各篇文案 / day4 策划）负责"账号策略与内容排期"；
- 本事实库负责"PaperForge 事实真实性"；
- 内容文案引用 PaperForge 事实时，优先引用本库 `CONTENT_EVIDENCE.md` 的事件 ID（如 E001、E002），保证口径统一。
